# Dioxus 0.7.10 Real-Time and Streaming Rules

Use this context only when a Dioxus full-stack task needs live events, bidirectional communication, streamed values, or streamed files.

## 1. Select the smallest correct transport

Use this order:

1. Use a normal server function and `use_action` for one request and one response.
2. Use `ServerEvents<T>` for server-to-client events.
3. Use `Streaming<T, E>` for a typed stream over HTTP.
4. Use `Websocket<ClientEvent, ServerEvent>` for persistent bidirectional messages.
5. Use `FileStream` or `ByteStream` for file or raw-byte transfer.

Do not use a WebSocket for a normal request. Do not poll when a native event stream is appropriate.

## 2. Use typed messages

Define shared serializable request, response, and event types in Rust.

For WebSockets, use separate client and server event enums:

```rust
#[derive(serde::Serialize, serde::Deserialize)]
enum ClientEvent {
    SendMessage(String),
}

#[derive(serde::Serialize, serde::Deserialize)]
enum ServerEvent {
    Message(String),
}
```

Do not pass unstructured JSON strings when a typed enum can represent the protocol.

## 3. Use the Dioxus WebSocket API

Create the client connection with `use_websocket`.

Return a typed WebSocket from a server function:

```rust
#[get("/api/socket", options: WebSocketOptions)]
async fn socket(
    options: WebSocketOptions,
) -> Result<Websocket<ClientEvent, ServerEvent>> {
    Ok(options.on_upgrade(|mut socket| async move {
        while let Ok(event) = socket.recv().await {
            // Process typed events.
        }
    }))
}
```

Use `send`, `recv`, connection status, and Dioxus reconnection behavior.

Do not use raw Axum WebSocket extraction or create a second client connection library.

## 4. Make connection dependencies explicit

Signals read by the `use_websocket` initializer are reactive connection dependencies. A change can cause reconnection.

Use this behavior only for values that define the connection, such as identity, room, or endpoint configuration.

Do not capture frequently changing UI state in the initializer.

## 5. Use server-sent events for one-way notifications

Return `ServerEvents<T>` when only the server sends events.

Use a serializable event enum. Stop the producer loop when sending fails because the client disconnected.

Do not base64-encode large binary data into server-sent events. Use `ByteStream` or `FileStream` instead.

## 6. Use typed HTTP streams for streamed values

Use `Streaming<T, E>` with a Dioxus encoding such as JSON, CBOR, Postcard, MessagePack, or Rkyv.

Select the encoding from compatibility and performance requirements. Use JSON unless a binary encoding gives a measured benefit.

Use `TextStream` for plain text. Do not invent a framing protocol that a Dioxus encoding already provides.

## 7. Stream files and bytes

Use `FileStream` when file name, size, content type, and disposition are part of the operation.

Use `ByteStream` for opaque generated bytes.

Validate names, expected sizes, content types, and destination paths on the server. Apply explicit transfer limits.

Do not collect a large upload or download into memory before processing it.

## 8. Handle cancellation and disconnects

End producer tasks when the receiver disconnects. Cancel client loops when their component or action ends.

Use bounded channels or another explicit backpressure policy for streams that can produce data faster than a client can consume it.

Do not leave detached producer tasks running after the connection closes.

## 9. Keep shared state outside connection handlers

Use `LazyLock` or `dioxus::fullstack::Lazy` for process-wide rooms, channels, or services.

Keep per-connection identity and transient state inside the connection handler. Use a request extension only when request processing creates that state.

Do not create one global mutable collection without a cleanup and concurrency policy.

## 10. Authenticate before accepting data

Resolve identity and permission on the server before joining a channel or processing events.

Validate every client event. Apply message-size, rate, and resource limits.

Do not trust typed deserialization as authorization or business validation.

## 11. Keep custom transport code as an exception

Use direct Axum streaming, raw WebSockets, or a custom protocol only when Dioxus cannot represent the required transport behavior.

Keep that exception at the server boundary. Continue to use Dioxus components, state, and typed domain messages in the application.
